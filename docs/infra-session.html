Infra requirements · Tech stack

How the pieces talk to each other

Browser loads the React bundle from Nginx, then calls the Django API. For files, the API returns a pre-signed URL and the browser uploads/downloads directly to object storage — file bytes never pass through the backend. Celery workers read/write storage directly. Beat is the single scheduler.

Infra requirements · Sizing

Baseline to start with

Pilot / training

1–2 nodes

  • 1 × e2-standard-2 (template default)
  • API 1–2, Worker 1, Recreate strategy
  • DB 2 vCPU / 3.75 GB, zonal
  • A few facilities

Standard state rollout

3–4 nodes

  • e2-standard-2 pool
  • API 2→4, Worker 1→2
  • DB 2 vCPU / 3.75 GB + 1 read replica
  • Where most live instances sit

Large / multi-module

5+ nodes

  • DICOM, many plugs, heavy analytics
  • HPA on API and Worker
  • Bigger DB tier, REGIONAL HA
  • Scale on measured load

Grow on signals, not facility count alone: API CPU, Celery queue depth, DB CPU/connections, node memory.

Scoping & provisioning

Autoscaling with HPA

Backend API

  • HPA on CPU, template default 2 → 6 pods at 80%
  • api_autoscaling_min/max_replicas in helm_config
  • Scale-down waits 15 min (stabilizationWindowSeconds: 900)

Celery Worker

  • Same HPA pattern, default 2 → 6 at 80%
  • Live example: 2 → 8 pods at 60% CPU
  • Watch queue depth — the alert fires at > 200 waiting tasks
Beat is never scaled — one scheduler only. More replicas multiply requests; check node allocatable before raising the max.
Scoping & provisioning

Checklist

Scope

  • Number of facilities, users, go-live phases
  • Modules and plugs (ABDM, scribe, DICOM, payments)
  • Analytics needed? → Metabase
  • Hosting: cloud / on-prem, data residency
  • Domains: web, API, Metabase, DICOM

Provision

  • GCP project, billing, state bucket
  • tfvars → Secret Manager (tofu-tfvars-<env>)
  • Apply pre-infra → KMS → infra → deploy
  • Node pool, DB tier, replicas, HPA limits
  • DNS + TLS, Cloud Armor, alert emails
  • Backups / PITR verified, restore tested

Environment setup · Metabase

Dashboards with Metabase

Optional — only for analytics

  • Chart metabase/metabase:v0.63.13, port 3000, health /api/health
  • Own metadata DB (Cloud SQL db-f1-micro)
  • Plan ~1.5 Gi RAM for the pod

Connect to CARE data — two ways

  1. Read replica (GCP default): Cloud SQL replica, reporting never loads the primary
  2. Read-only SQL user on the CARE DB — simpler, works anywhere, including on-prem
Never give Metabase a read-write user. Prefer the replica for heavy dashboards.
Recap

Start small, scale on signals

3 small nodes + a 2-vCPU Postgres runs a real state HMIS today. Use HPA for API and workers, promote staging → production by commit, and add Metabase only when you need analytics.
