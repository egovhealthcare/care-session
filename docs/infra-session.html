Infra requirements · Tech stack

How the pieces talk to each other

Browser loads the React bundle from Nginx, then calls the Django API. For files, the API returns a pre-signed URL and the browser uploads/downloads directly to object storage — file bytes never pass through the backend. Celery workers read/write storage directly. Beat is the single scheduler.

Infra requirements · Sizing

Baseline to start with

Pilot / training

1 node

  • Single-node cluster: 2 vCPU / 8 GB
  • Use the minimum resources in sample.tfvars
  • 1 copy of each service
  • Database: 2 vCPU / 3.75 GB

Standard state rollout

~10 vCPU · 40 GB

  • Total for the whole instance, database included
  • 2–4 API copies, 1–2 workers
  • Database + 1 read replica
  • Where most live instances run

Large / multi-module

13+ vCPU · 48+ GB

  • DICOM, many plugs, heavy analytics
  • Autoscaling on API and workers
  • Bigger database, high availability
  • Scale on measured load

These are the defaults we ship and they work in most cases. You are free to change node size and per-component resources to fit your load.

Scoping & provisioning

Autoscaling with HPA

Autoscaling is a built-in Kubernetes feature (Horizontal Pod Autoscaler). We use it to add or remove CARE backend and worker copies automatically based on usage.

Backend API

  • HPA on CPU, template default 2 → 6 pods at 80%
  • api_autoscaling_min/max_replicas in helm_config
  • Scale-down waits 15 min (stabilizationWindowSeconds: 900)

Celery Worker

  • Same HPA pattern, default 2 → 6 at 80%
  • Live example: 2 → 8 pods at 60% CPU
  • Watch queue depth — the alert fires at > 200 waiting tasks
Scoping & provisioning

Checklist

Decide first

  • Environments: dev, staging, QA, production
  • Where it runs: GCP, AWS, any other cloud, or on-prem
  • Optional components: Metabase, DICOM, AI scribe
  • Plugs and features needed
  • Domains: every public component gets its own subdomain (web, API, Metabase, DICOM)

Set up

  • Cloud project and billing
  • Fill in the config and run the gcp_template modules in order
  • Pick node size, database size and autoscaling limits
  • DNS and HTTPS for each subdomain, alert emails
  • Backups verified, restore tested
  • Guard against accidental deletion: GCP organisation policies and deletion protection (other clouds have similar safeguards)

Environment setup · Staging

Staging: configure, test, train

Where everything happens first

Every change lands on staging first, then production — so no surprises in production.

  • Dedicated GCP project with the full gcp_template stack
  • Builds from the develop ref of care / care_fe
  • New plugs, value sets, roles and config tested here
  • Training runs on staging, never production

How the auto-deploy-states pipeline works

  1. Build: build care and care_fe images from the chosen commit, push to Artifact Registry
  2. Deploy: pick the environment and image tags
  3. Check the images exist, else stop
  4. Write the new tags into the environment's config (Secret Manager)
  5. Run OpenTofu plan and open a GitHub issue with the plan
  6. Wait for an approver to comment approved (or denied, or time out)
  7. On approval, apply — the new version goes live

Two branches, one codebase

  • Staging builds care and care_fe from develop
  • Every production instance builds from the production branch
  • Set per environment in build_config.json (env/)
  • Promotion = move the tested commits from develop to production

One run, every instance

  • Deploy option production picks every environment marked as production in its config
  • Each instance gets its own plan and its own approval issue
  • One failing instance does not stop the others
  • Only one deploy at a time per instance

Guard rails

  • Pull requests are checked for valid config (validate.yaml)
  • Deploy stops if the image tag does not exist
  • Only named approvers can approve; no answer in 45 min cancels
  • Rollback: deploy again with the previous image tag
Environment setup · Metabase

Dashboards with Metabase

Optional — only for analytics

  • Needs its own small database to store dashboards, questions and users — on GCP we provision a separate Cloud SQL instance for it
  • Runs as a single pod and is memory-heavy: plan about 2 GB RAM (live instances use ~1.4 GB)
  • Installed from the metabase chart, served on its own subdomain

Connect to CARE data — two ways

  1. Read replica (GCP default): Cloud SQL replica, reporting never loads the primary
  2. Read-only SQL user on the CARE DB — simpler, works anywhere, including on-prem

Prefer the replica for heavy dashboards.

Recap

Start small, scale on signals

3 small nodes + a 2-vCPU Postgres runs a real state HMIS today. Use HPA for API and workers, promote staging → production by commit, and add Metabase only when you need analytics.
